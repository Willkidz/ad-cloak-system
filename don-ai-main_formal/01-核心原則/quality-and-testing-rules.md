# 品質標準

本文件定義 AI 產出的品質評分標準。任務完成前，AI 必須根據本標準對自己的產出進行 1-10 分的自我評估。**低於 8 分的產出需自行修正後才能交付。**

---

## 評分維度

### 程式碼品質（適用於所有程式碼產出）

| 分數 | 標準 |
| :--- | :--- |
| 9-10 | 程式碼簡潔、無冗餘、有完整錯誤處理、遵循專案技術規範、通過 lint 檢查 |
| 7-8 | 功能正確、有基本錯誤處理、大致遵循規範，但可能有小瑕疵 |
| 5-6 | 功能基本正確，但缺少錯誤處理或不遵循規範 |
| 3-4 | 功能部分正確，有明顯 bug 或安全風險 |
| 1-2 | 無法運行或有嚴重安全漏洞 |

### 文件品質（適用於所有 Markdown 文件產出）

| 分數 | 標準 |
| :--- | :--- |
| 9-10 | 包含完整 YAML frontmatter（符合 `01-核心原則/doc-standards-spec.md`）、結構清晰、資訊準確、有交叉引用 |
| 7-8 | 包含 frontmatter、結構合理、資訊基本準確 |
| 5-6 | 缺少 frontmatter 或結構混亂 |
| 3-4 | 資訊不準確或嚴重過時 |
| 1-2 | 內容錯誤或與主題無關 |

### 部署品質（適用於所有部署操作）

| 分數 | 標準 |
| :--- | :--- |
| 9-10 | 零停機部署、有回滾方案、部署後驗證通過、已更新文件 |
| 7-8 | 部署成功、功能正常、有基本驗證 |
| 5-6 | 部署成功但未驗證或缺少回滾方案 |
| 3-4 | 部署造成短暫停機或部分功能異常 |
| 1-2 | 部署失敗或造成系統不可用 |

## 偷懶行為防護規則（Lazy Behavior Guard）

> **補充說明**：AI 代理在生成代碼時，傾向於選擇「阻力最小的路徑」，快速完成核心功能但跳過防禦性編程。本節規則作為「程式碼品質」評分的具體強制標準，確保 AI 不會因為偷懶而讓代碼品質低於 8 分。

<rule id="lazy-1-error-handling">
**完整的錯誤處理（強制）**：在編寫任何可能發生異常的代碼（網路請求、檔案讀寫、資料庫操作）時：
- 必須包含完整的 `try-catch` 或等效的錯誤處理邏輯。
- **絕對不允許使用空的 catch 區塊**（吞掉異常）。
- 遇到錯誤時，不能只是返回 `null` 或 `false`，必須拋出帶有明確訊息的異常，或返回標準化的錯誤物件。

違反此規則，程式碼品質評分直接不得超過 6 分。
</rule>

<rule id="lazy-2-logging">
**強制日誌記錄（Logging）**：代碼中不能只有業務邏輯，必須包含可觀測性設計：
- 在所有關鍵操作（狀態變更、外部 API 呼叫）的入口與出口添加適當級別的日誌（Info/Debug）。
- 在異常捕獲處必須記錄錯誤日誌（Error），且**日誌中必須包含足夠的上下文資訊**（如 Request ID、用戶 ID、導致錯誤的具體參數值），以便後續排查。
</rule>

<rule id="lazy-3-resource-cleanup">
**資源管理與清理**：在處理需要手動釋放的資源（資料庫連線、檔案控制代碼、網路 Socket）時，必須確保資源在操作完成後被正確關閉。強制使用 `finally` 區塊、`using` 語句（TypeScript）或 `with` 語句（Python）等機制，確保即使發生異常，資源也不會洩漏。
</rule>

<rule id="lazy-4-edge-cases">
**主動邊界思考（強制）**：在實現任何核心演算法或資料處理邏輯時，AI 必須在代碼中主動處理**至少三種邊界情況（Edge Cases）**。特別注意防範「差一錯誤」（Off-by-one error）、空集合處理以及極端大數值的溢出問題。

違反此規則，程式碼品質評分直接不得超過 7 分。
</rule>

### 偷懶行為的快速自查

在交付代碼前，AI 必須確認：

- [ ] 所有 `catch` 區塊都有實際的錯誤處理邏輯（非空）
- [ ] 所有關鍵操作都有日誌記錄，且日誌包含上下文資訊
- [ ] 所有外部資源（連線、檔案）都有對應的關閉/清理邏輯
- [ ] 已主動思考並處理了至少三種邊界情況

> **TL;DR**: AI 生成的測試天生偏向 Happy Path，只測「一切正常」的情況，對邊界條件、錯誤路徑、併發場景視而不見。本文件強制要求 AI 在生成任何測試時，必須同時覆蓋四個維度：正常路徑、邊界條件、錯誤路徑、安全驗證。少一個維度就不算完成。

# AI 測試深度規則

## 為什麼需要這條規則

AI 代理在生成測試時，傾向於只驗證「最理想的使用情境」。例如測試一個用戶註冊 API，AI 會測試填寫所有正確資料的情況，卻不會測試資料庫連線超時、用戶重複點擊提交按鈕、或輸入特殊字元的場景。這種「Happy Path 偏差」會讓 CI/CD 全部亮綠燈，但代碼在生產環境遇到真實流量時直接崩潰。

---

## 強制測試四維度

每次 AI 生成測試代碼，**必須明確覆蓋以下四個維度**，缺一不可：

<rule id="test-depth-1-happy-path">
### 維度 1：正常路徑（Happy Path）
驗證標準輸入得到預期輸出。這是最基本的，但不能只有這個。
</rule>

<rule id="test-depth-2-boundary">
### 維度 2：邊界條件（Boundary Conditions）
必須測試以下邊界，不能跳過：

| 邊界類型 | 必測的具體情況 |
| :--- | :--- |
| 數值邊界 | 最大值、最小值、零值、負數、超出範圍的值 |
| 字串邊界 | 空字串、超長字串、含特殊字元（`<>'"&`）、含 Unicode |
| 集合邊界 | 空陣列/集合、只有一個元素、超大資料集 |
| 時間邊界 | 時區轉換、閏年、Unix 時間戳邊界 |
</rule>

<rule id="test-depth-3-error-path">
### 維度 3：錯誤路徑（Error Path）
必須測試系統在出錯時的行為，而不只是正常時的行為：

- **外部依賴失敗**：資料庫連線超時、第三方 API 回傳 500、網路斷線。
- **無效輸入**：缺少必填欄位、型別錯誤、格式不符。
- **空值處理**：函數收到 `null`、`undefined` 或空物件時不能崩潰。
- **異常捕獲驗證**：確認 `catch` 區塊確實有被執行，而不是被吞掉。

> **禁止事項**：測試代碼不能直接複製實現代碼的邏輯來斷言結果。如果實現代碼的排序邏輯是錯的，測試也跟著錯，等於沒測。測試必須基於**業務需求的獨立預期值**來驗證。
</rule>

<rule id="test-depth-4-concurrent">
### 維度 4：安全與併發（Security & Concurrency）
對於涉及用戶輸入或狀態變更的功能，還必須測試：

- **重複提交防禦**：用戶快速點擊兩次提交按鈕，系統是否能正確處理？
- **競態條件**：兩個請求同時修改同一筆資料，結果是否符合預期？
- **輸入清理驗證**：確認 SQL 注入字串（如 `'; DROP TABLE users; --`）被正確攔截。
</rule>

---

## 測試生成的自我檢查清單

AI 在交付測試代碼前，必須逐項確認：

- [ ] 是否有測試資料庫連線失敗或 API 超時的降級策略？
- [ ] 是否有測試空值、空集合的邊界情況？
- [ ] 測試代碼是否只是單純複製了實現代碼的邏輯（如果是，必須重寫）？
- [ ] 是否有測試用戶輸入中含有特殊字元或注入字串？
- [ ] 是否有測試重複提交或高併發的場景（如果功能涉及狀態變更）？

# 防護型自動學習迴圈

## 1. 目的

讓 AI 能夠從 `.ai/error-log.md` 中自動學習並演化出新的規則，同時透過完善的防護機制，確保 AI 絕對不會學到錯誤的規則，避免引發比原始錯誤更嚴重的連鎖反應。

---

## 2. 三層防護架構

為了防止自我修正盲點、災難性遺忘與負遷移，本系統採用借鑒軟體工程金絲雀部署的「三層防護架構」：

<rule id="learn-layer1">
### 第一層：規則提煉 (Rule Proposal)

AI 在執行 SOP 4 (Offboarding) 時，必須檢查本次 session 是否有新的錯誤修復。如果有，AI 應將錯誤經驗提煉成「規則草稿」，並存入 `.ai/pending-rules.md`。

**注意**：規則草稿在此階段**不直接生效**，僅作為暫存。
</rule>

<rule id="learn-layer2">
### 第二層：金絲雀試用期 (Canary Trial)

新規則草稿會帶有 `[試用中]` 標籤與生效日期。在接下來的 7 天內，AI 僅在**低風險任務**中參考這些試用規則進行觀察。這限制了潛在錯誤規則的「爆炸半徑」，確保即使規則有誤，也不會影響核心系統。
</rule>

<rule id="learn-layer3">
### 第三層：轉正或淘汰 (Verification or Rejection)

- **轉正**：7 天試用期滿後，如果該規則沒有引發任何負面影響或回歸錯誤，AI 應移除 `[試用中]` 標籤，將其轉為正式規則，並寫入 `.ai/error-log.md` 頂部的「已驗證規則」區塊。
- **淘汰**：如果在試用期間發現該規則導致了新的問題，AI 必須立即停止使用該規則，將其標記為 `[已淘汰：具體原因]`，並歸檔保留紀錄，以防未來重複提出相同的錯誤規則。
</rule>

---

## 3. 規則草稿標準格式

所有存入 `.ai/pending-rules.md` 的規則草稿，必須嚴格遵循以下格式：

| 欄位 | 說明 |
| :--- | :--- |
| **觸發條件** | 在什麼具體情況下適用此規則？ |
| **錯誤現象** | 如果不遵守此規則，會發生什麼錯誤？ |
| **正確做法** | 應該如何正確執行？ |
| **來源** | 源自哪次 session 的哪一項錯誤紀錄（附上日期與錯誤簡述） |
| **信心等級** | 評估此規則的可靠性（高 / 中 / 低） |

<example>

```markdown
### 規則草稿：ad_code 大小寫統一 [試用中]

- **觸發條件**：任何涉及 ad_code 查詢的 SQL 或 JavaScript 代碼
- **錯誤現象**：ad_code 大小寫不一致導致 line_config 查詢失敗，返回空結果
- **正確做法**：所有 ad_code 在使用前必須先 `.toUpperCase()` 轉為大寫
- **來源**：2026-03-26 session，修復 CX06 查詢失敗問題
- **信心等級**：高
- **生效日期**：2026-03-26
- **試用期截止**：2026-04-02
```
</example>

# Code Review 標準與流程

## 1. 為什麼需要這個規則

雖然 AI 會進行自我評估，但缺乏外部視角的審查可能導致潛在問題被忽略，或代碼風格、架構決策無法保持一致。這個規則確保每次程式碼變更都經過嚴格的品質把關。

---

## 2. 審查流程

<rule id="cr-process">

### 2.1 觸發時機

- **重大功能變更**：新增 API 端點、修改核心邏輯、變更資料庫結構。
- **複雜任務**：涉及 3 個以上文件修改的任務。
- **安全性敏感**：涉及驗證、加密、權限控制的代碼。

### 2.2 審查角色

- **Reviewee (被審查者)**：負責編寫代碼並提交審查請求。
- **Reviewer (審查者)**：負責審查代碼並提出改進建議。可以是另一位 AI 代理或人類開發者。

### 2.3 審查步驟

1. **提交請求**：Reviewee 說明修改內容、原因及測試結果。
2. **執行審查**：Reviewer 根據「審查重點」逐項檢查。
3. **提出意見**：Reviewer 提出具體、客觀的改進建議。
4. **回應與修正**：Reviewee 針對意見進行修正或說明理由。
5. **最終確認**：Reviewer 確認修正後，給予通過（Approve）。

</rule>

---

## 3. 審查重點 (Checklist)

<rule id="cr-checklist">

| 審查維度 | 檢查項目 |
| :--- | :--- |
| **1. 功能正確性** | 代碼是否實現了需求？是否處理了邊界情況？是否有邏輯漏洞？ |
| **2. 安全性** | 是否有硬編碼的 API Key/Token？是否驗證了外部輸入？是否有 SQL 注入風險？ |
| **3. 效能與資源** | 是否有冗餘的循環或請求？是否使用了快取？是否符合 Workers 輕量化要求？ |
| **4. 錯誤處理** | 是否有完整的 `try-catch`？錯誤訊息是否清晰？是否記錄了必要的日誌？ |
| **5. 可讀性與風格** | 是否遵循專案命名規範？代碼結構是否清晰？是否有必要的註釋？ |
| **6. 文檔同步** | `CHANGELOG.md` 是否更新？相關的 `_index.md` 是否更新？ |

</rule>

## 4. 溝通規範

<rule id="cr-communication">

- **具體性**：不要只說「這裡寫得不好」，要說「這裡的循環可以優化為批量處理，以減少 API 呼叫次數」。
- **客觀性**：針對代碼而非個人。使用「建議改為...」或「這裡可能有...風險」。
- **建設性**：提出意見的同時，盡可能提供改進的範例代碼。

</rule>
