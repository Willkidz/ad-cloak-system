## 二、 六大核心問題

### 問題 1：v2 五層分類架構與實踐脫節

<rule id="issue-1">
原定義的 `state` / `convention` / `architecture` / `issue_resolved` / `context` 五層分類架構已名存實亡。分析發現，實際使用了 11 種分類，其中 6 種（如 `ban_analysis`, `competitor_analysis`）不在原架構內，而架構中定義的 `state` 分類從未使用過。這表明缺乏統一的分類標準，導致記憶結構混亂。
</rule>

### 問題 2：重要度 (Importance) 欄位完全失效

<rule id="issue-2">
在 298 筆記憶中，重要度欄位的值全部為 0，導致該欄位完全失效。AI Agent 在啟動時無法通過重要度篩選優先讀取的記憶，被迫載入所有記憶，造成嚴重的 Token 浪費。
</rule>

### 問題 3：大量過時記憶殘留（至少 74 筆）

<rule id="issue-3">
經統計，至少有 74 筆記憶包含已過時的資訊，例如引用已遷移的服務 (n8n)、已廢棄的技術 (DataTables) 或已刪除的資源 (Worker)。這些過時記憶不僅浪費資源，更有可能誤導 AI Agent 做出錯誤的判斷。

| 過時類型 | 筆數 | 說明 |
| :--- | :--- | :--- |
| 仍引用雲端 n8n | 11 筆 | 已遷移到自架設環境 |
| 提到已廢棄的 DataTables | 16 筆 | 已遷移到 D1 資料庫 |
| 提到已刪除的工作流 | 10 筆 | 「每日統計報告」已刪除 |
| 提到已刪除的 Worker | 9 筆 | `gv-liff`、`godview-clicks` 已刪除 |
| 使用舊的 type 命名 | 7 筆 | `type=master` 已改為 `type=ads` |
| 仍引用 Lead 事件 | 9 筆 | 已改為 `CompleteRegistration` 事件 |
| 提到已刪除的 Token Mapping | 12 筆 | 相關工作流已刪除 |
</rule>

### 問題 4：充斥大量一次性操作日誌

<rule id="issue-4">
約有 31 筆記憶屬於純粹的操作紀錄（例如「已完成 X」、「已修復 Y」）。這類一次性事件在完成後即失去長期儲存價值，卻佔用了寶貴的記憶空間。
</rule>

### 問題 5：52 筆記憶無法歸屬特定專案

<rule id="issue-5">
高達 17.4% 的記憶因缺乏專案關鍵字而無法歸屬，導致 AI Agent 在讀取時難以判斷其相關性。這些記憶包括未標記專案的像素 ID、缺乏中文說明的系統架構描述等。
</rule>

### 問題 6：存在內容重複的記憶

<rule id="issue-6">
初步發現至少 3 組內容幾乎完全相同的記憶，這直接導致了儲存空間和讀取 Token 的浪費。
</rule>

## 三、 改善方案建議

### 方案 A：記憶大掃除（立即執行）

此為短期最有效的方案，旨在快速清理無效記憶，降低系統負載。

<step>1. **清理過時記憶**：刪除或更新至少 74 筆已識別的過時記憶。</step>
<step>2. **移除操作日誌**：刪除約 31 筆純操作日誌型記憶。</step>
<step>3. **合併重複內容**：合併 3 組內容重複的記憶。</step>
<step>4. **補充專案標記**：為 52 筆未分類記憶補上正確的專案標籤。</step>

> **預期效果**：預計可將記憶總數從 298 筆減少至約 190 筆（-36%），使 Agent 啟動時讀取的 Token 減少約三分之一，並消除過時資訊的誤導風險。

### 方案 B：重新定義分類架構（中期）

若決定繼續使用 Memory API，則需重新設計分類架構以確保其一致性與實用性。

<rule id="recommendation-B">
建議將現行架構優化為 `current_state`、`convention`、`architecture`、`lesson_learned`、`decision_log` 和 `credential` 六大分類。核心思想是：
- **用 `current_state` 取代不斷新增的狀態記錄**，每個專案只保留一份定期覆蓋的最新狀態快照。
- **用 `lesson_learned` 取代 `issue_resolved`**，只保留從問題中學到的「教訓」，而非一次性的「操作紀錄」。
- **用 `decision_log` 取代混雜的 `context`**，專注記錄「為什麼這樣決定」，而非「做了什麼」。
</rule>

### 方案 C：啟用重要度分級（中期）

同樣，若保留 Memory API，必須啟用重要度分級，以實現高效的選擇性載入。

<rule id="recommendation-C">
建議將重要度分為 1 到 5 級，並規定 AI Agent 在啟動時只讀取重要度為 4-5 級的核心記憶（如核心架構、API 金鑰、當前狀態等）。

| 重要度 | 定義 | Boot 時讀取 |
| :--- | :--- | :--- |
| 5 | 核心架構、API 金鑰、當前狀態 | **必讀** |
| 4 | 重要規範、協作規則 | **必讀** |
| 3 | 決策紀錄、教訓 | 按需讀取 |
| 2 | 競品情報、素材規範 | 按需讀取 |
| 1 | 歷史紀錄、已解決問題 | 不讀 |

> **預期效果**：預計可將啟動時讀取的記憶從 298 筆降至約 50 筆，Token 消耗減少約 83%。
</rule>

### 方案 D：遷移至交接文件（長期根本方案）

此方案主張用一份經人工審核、高質量、結構化的「全專案交接文件」徹底取代現有的 Memory API。

<rule id="recommendation-D">
**核心邏輯**：與其讓 AI 在大量低質量、未經整理的記憶中大海撈針，不如直接提供一份精煉、準確、完整的核心知識文件。這份文件將成為 AI 的唯一真相來源。

**執行方式**：
- 停用 `manus-memory-api` Worker 並歸檔 `manus-memory` D1 資料庫。
- 將所有現存記憶的精華部分整合進統一的交接文件中 `[待確認：文件具體路徑]`。
- AI Agent 啟動時直接讀取該文件，不再呼叫 Memory API。
</rule>

## 四、 結論與建議執行路徑

綜合分析，當前記憶系統的維護成本高昂且效率低下。與其在現有基礎上不斷修補（方案 B 和 C），不如採取更為徹底的改革（方案 A 和 D）。

> **最終建議**：我們強烈建議採用**最精簡的執行路線**。首先，立即執行「**方案 A：記憶大掃除**」，快速清理現有系統中的無效資訊，降低短期風險。隨後，全力推進「**方案 D：遷移至交接文件**」，待交接文件完善後，徹底切換至新的知識管理模式。此路徑完成後，方案 B 和 C 將不再必要，從而實現對 AI 記憶架構的根本性優化。

| 優先級 | 方案 | 工作量 | 預期效果 | 核心理由 |
| :--- | :--- | :--- | :--- | :--- |
| **1** | **A：記憶大掃除** | 低 (2-3 小時) | 高 | 立即降低風險與成本 |
| **2** | **D：改用交接文件** | 中 (已完成 80%) | 最高 | 從根本上解決問題 |
| 3 | B：重新定義分類 | 中 | 中 | 若方案 D 成功則無需執行 |
| 4 | C：啟用重要度分級 | 低 | 中 | 若方案 D 成功則無需執行 |
