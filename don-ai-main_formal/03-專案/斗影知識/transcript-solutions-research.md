> **TL;DR**: 本報告整合四份既有研究結果，確認斗影知識系統目前摘要品質的核心瓶頸主要不在摘要模型本身，而在於**逐字稿上游品質不足**；同時，TikHub `fetch_one_video_v2` 在 9 支抖音影片的實測中，**原生字幕命中率為 0%**，因此不能再把「直接從 TikHub 取得字幕」視為可依賴主路徑。綜合 V1 與 V2 的方案調查後，建議採用**分層逐字稿策略**：先以 **Apify** 類工具嘗試抓取現成字幕，再以 **騰訊雲 ASR** 或 **GPT-4o-mini / GPT-4o-mini-transcribe** 作為補底轉寫方案；若後續有較強自建能力，則可進一步評估 **FunASR** 作為中文開源自建方案。[1] [2] [3] [4]

# 抖音逐字稿解決方案整合研究

## 1. 背景與調查目的

斗影知識系統目前已具備影片收錄、逐字稿保存、AI 摘要與搜尋展示能力，但既有抽樣分析顯示，摘要品質的穩定性高度依賴逐字稿品質。當影片屬於短秒數、高密度、專有名詞密集的工具型內容時，若逐字稿缺乏標點、專有名詞誤辨嚴重，摘要就容易退化為「格式完整但資訊空洞」的結果。因此，本次調查的真正目標，不是單純找一個「能轉寫音訊」的服務，而是重新評估整條逐字稿上游鏈路的可行性、成本、中文能力、批量能力與後續可擴展性。[1]

本報告整合兩輪方案研究。第一輪調查主要比較 **OpenAI Whisper / 阿里雲語音識別 / Apify + AI 後處理 / TikHub 字幕 / RapidAPI** 等可直接納入現有流程的方案；第二輪調查則進一步擴展到**官方/半官方途徑、雲端 ASR、開源自建、第三方工具與 AI 多模態**五大類，將評估範圍擴展至 15 個以上具體方案。除此之外，本報告也把 TikHub 原生字幕欄位實測結果與上游品質問題分析納入同一份決策文檔，形成可直接指導後續實作的完整依據。[1] [2] [3] [4]

| 整合來源 | 核心貢獻 | 對本報告的作用 |
| :--- | :--- | :--- |
| `summary-quality-analysis.md` | 說明摘要失真與逐字稿噪音的因果鏈 | 用於界定問題本質 |
| `tikhub-subtitle-test-result.md` | 驗證 TikHub 原生字幕欄位是否可直接利用 | 用於否定單一路徑假設 |
| `transcript-solutions-comparison.md` | 提供 V1 的可落地方案比較與流程設計 | 用於保留早期實作導向觀點 |
| `transcript-solutions-v2.md` | 擴展到 15+ 方案的更完整市場調查 | 用於完善技術選型全景 |

## 2. 問題本質：目前的瓶頸其實是逐字稿上游品質

現有系統抽樣結果顯示，摘要質量的波動並不是單一模型提示詞失敗，而是逐字稿上游語料品質不足所造成的系統性問題。具體來看，既有逐字稿普遍存在**缺乏標點、斷句鬆散、工具名與品牌名誤辨、同音錯字偏多**等現象。這些問題會直接削弱後續摘要模型對於「工具名稱、功能、操作步驟與適用場景」的抽取能力，尤其在抖音工具型短片場景中更為明顯。[1]

換句話說，若逐字稿源頭本身就把 `Midjourney`、`Cursor`、`Cloud Code` 等名稱辨識錯誤，後續即使再換更好的摘要 Prompt，模型也只會在低品質文本上做更漂亮的猜測，而無法穩定輸出高可信知識。因此，逐字稿方案的選型不能只看「能不能轉寫」，而必須優先關注**中文專有名詞辨識能力、熱詞支援、批量處理能力與成本可控性**。[1] [3] [4]

| 上游問題 | 典型表現 | 對下游摘要的直接影響 |
| :--- | :--- | :--- |
| 無標點與弱斷句 | 整段口語連寫 | 摘要模型難以切句與定位重點 |
| 專有名詞誤辨 | 工具名、品牌名、平台名變形 | 工具抽取失真、可信度下降 |
| 同音錯字 | 行業術語被誤轉為近音詞 | 功能與步驟判讀偏差 |
| 缺乏時間軸 | 無法快速人工回看與複核 | 品質抽檢成本高 |
| 原生字幕不可得 | 無法用低成本直接提取 | 必須建立補底 ASR 路徑 |

## 3. TikHub 原生字幕實測：單一路徑假設已被證偽

針對「是否可以直接依賴 TikHub 取得抖音原生字幕」這個關鍵假設，實測報告已給出相當明確的否定答案。測試以 `AI工具` 關鍵字取得 9 支抖音影片，再逐支檢查 `fetch_one_video_v2` 回傳 JSON 內與字幕相關的候選欄位，包括 `video.subtitleInfos`、`video.cla_info.caption_infos`、`interaction_stickers[*].auto_video_caption_info.auto_captions[*]`、`subtitle`、`caption`、`transcript` 等名稱。結果顯示，表面上雖有 5 支影片命中 `caption` 等字樣，但人工複核後可確認這些內容只是**貼文文案、文案索引或空值欄位**，而非可直接使用的字幕正文、字幕檔 URL 或字幕段落陣列。[2]

最重要的結論是：**原生字幕命中比例為 0/9 = 0%**。這代表 TikHub `fetch_one_video_v2` 至少在本次樣本下，並沒有提供可直接落地的原生字幕資料結構。因此，若系統設計仍以「TikHub 會帶回原生字幕」為前提，後續流程就會建立在錯誤假設之上。[2]

| 測試口徑 | 結果 | 判讀 |
| :--- | :--- | :--- |
| 測試影片數 | 9 支 | 來自 `AI工具` 搜尋結果 |
| 廣義關鍵字命中 | 5 支 | 只代表出現 `caption` 等字樣 |
| 真正原生字幕命中 | 0 支 | 無字幕正文、URL 或時間軸陣列 |
| 指定候選欄位 | 全數未命中 | `subtitleInfos`、`cla_info.caption_infos`、`auto_captions` 皆不可用 |
| 結論 | 不可依賴 TikHub 原生字幕 | 必須建立替代與補底方案 |

> 根據實測結果，`caption` 在命中樣本中是貼文文案，`text_extra[*].caption_start/end` 是文案偏移資訊，`interaction_stickers` 在命中樣本中均為 `null`，`is_subtitled` 也均為 `0`，因此不能把這些欄位視為逐字稿來源。[2]

## 4. V1 與 V2 整合後的方案全景

綜合兩輪研究，本次調查可整理為五大方案族群：**官方/半官方途徑、第三方現成字幕提取、雲端 ASR、開源自建 ASR、AI 多模態轉寫**。若按實際導入邏輯來看，真正可形成產品級方案的並不是單一服務，而是「先判斷有沒有現成字幕，再決定是否進入轉寫」的多層流程。[3] [4]

V1 的價值，在於它先把方案拆成實作導向的五個入口，尤其明確指出 **Apify + AI 後處理** 可以作為低成本捷徑，而 **阿里雲 / Whisper** 可以作為真正的 ASR 轉寫路徑。V2 則進一步把研究視野擴大到更完整的市場與技術面，補齊了 **騰訊雲、訊飛、Google、Azure、Deepgram、AssemblyAI、FunASR、SenseVoice、CapCut Cloud API、GPT-4o 系列** 等候選方案，讓選型依據不再只停留在單一供應商比較。[3] [4]

## 5. 重點方案比較：品質、成本與落地性

若只從斗影知識系統的現階段需求來看，真正值得投入的候選方案可以收斂為五條主線：**Apify 類現成字幕提取、騰訊雲 ASR、阿里雲 / 訊飛雲端 ASR、FunASR 自建、GPT-4o-mini 補底轉寫**。這五條路線分別對應不同的成本結構與技術風險。[3] [4]

| 方案 | 中文品質 | 熱詞能力 | 批量能力 | 月成本估算 | 落地難度 | 本次判斷 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| Apify 現成字幕提取 | 取決於原片字幕 | 無 | 高 | 約 $3–$10 或更低 | 低 | 適合作為第一層低成本捷徑 |
| 騰訊雲 ASR | 極佳 | 強，支援權重與同音替換 | 高 | 約 $15–$25 | 中 | 最佳中文商業化主力 |
| 阿里雲 ASR | 極佳 | 強 | 高 | 約 $15–$25 或更高 | 中 | 穩健備選 |
| 訊飛開放平台 | 頂尖 | 極強 | 高 | 約 $20–$35 | 中 | 高專名需求可考慮 |
| FunASR | 極佳 | 支援熱詞 | 高 | 軟體近零，硬體另計 | 高 | 中文開源最強自建方案 |
| faster-whisper | 良好 | 弱 | 高 | 軟體近零，硬體另計 | 中 | 泛用但不適合高專名場景 |
| GPT-4o-mini | 良好到極佳 | 無需顯式熱詞，靠上下文修正 | 中到高 | 約 $9 | 低 | 最適合作為智慧補底 |
| Deepgram / AssemblyAI | 一般 | 有限 | 高 | $25+ | 低 | 不建議作中文主路徑 |

從成本角度看，**Apify 類提取**在命中已有字幕時明顯最划算，因為不需要真正重新做 ASR；但它的結構性限制也非常清楚：只要原片沒有官方字幕，就直接失效。從中文品質與商業穩定性看，**騰訊雲 ASR** 與 **阿里雲 / 訊飛**仍是更穩妥的主力。若把「極致省錢」與「中文專有名詞能力」放在一起考慮，**FunASR** 是目前最值得關注的開源自建方案。若考慮「不想維護熱詞表，但希望模型能靠上下文修正術語」，則 **GPT-4o-mini** 類方案展現出很高的補底價值。[3] [4]

## 6. 核心決策：採用分層逐字稿策略，而不是單一 Apify 方案

結合上游品質分析與 TikHub 實測結果後，可以得出一個關鍵決策：**斗影知識系統不應再依賴單一來源取得逐字稿**。原因很直接。第一，TikHub 原生字幕不可依賴；第二，Apify 類工具雖便宜，但前提是影片原本就有可提取字幕；第三，真正影響摘要品質的是中文專有名詞與句意還原能力，因此系統必須保留高品質 ASR 補底層。[1] [2] [3] [4]

因此，最合理的架構不是「在多個方案中選一個」，而是建立**分層逐字稿策略**：

1. 第一層先嘗試 **Apify** 或同類工具抓現成字幕，以最小成本處理已帶字幕影片。
2. 若第一層失敗，第二層進入 **騰訊雲 ASR** 或 **GPT-4o-mini / transcribe** 補底轉寫。
3. 若後續追求更低單位成本且能承擔維運，可在第三階段評估以 **FunASR** 取代部分雲端 ASR 工作負載。[3] [4]

| 層級 | 建議方案 | 啟動條件 | 主要目的 |
| :--- | :--- | :--- | :--- |
| Layer 1 | Apify 現成字幕提取 | 影片可能已有現成字幕 | 以最低成本直接取得可用逐字稿 |
| Layer 2A | 騰訊雲 ASR | Layer 1 無結果，且追求穩定中文品質 | 補足主流中文轉寫需求 |
| Layer 2B | GPT-4o-mini / transcribe | Layer 1 無結果，且內容專名多或語義複雜 | 用上下文理解修正專有名詞 |
| Layer 3 | FunASR 自建 | 流量提升且需長期壓低單位成本 | 建立可控的中文自建能力 |

## 7. 為什麼優先推薦騰訊雲 ASR + GPT-4o-mini 補底

在所有候選方案中，**騰訊雲 ASR** 與 **GPT-4o-mini** 的組合，最符合斗影知識系統現階段「品質優先、成本可控、接入難度中低」的平衡目標。騰訊雲 ASR 的優勢，在於其對中文場景的成熟度高，尤其**熱詞權重調整與同音替換**能力，對於抖音工具型內容中大量品牌名、平台名、英中混講術語的場景特別重要。這使它比單純泛用型 ASR 更適合作為系統級主力方案。[4]

而 **GPT-4o-mini** 的價值，則不在於取代所有 ASR，而在於它能在專有名詞密集、語境複雜、口語跳躍較強的片段裡，靠上下文理解自動修正一些傳統 ASR 難以處理的術語與關係，且整體成本已下降到大約 **$9 / 月** 的量級，具備很好的補底性價比。[3] [4]

相較之下，單純使用 **faster-whisper** 雖然便宜，但缺乏原生熱詞；單純依賴 **Apify** 則受限於是否有現成字幕；而完全轉向 **FunASR 自建** 雖然潛力很高，但對現階段系統來說，還需要額外 GPU、推理與維運投入。因此，以商業化與快速落地視角來看，**「Apify 先撿現成字幕 → 騰訊雲 / GPT-4o-mini 補底」**是目前最穩妥的實施路徑。[3] [4]

## 8. 對斗影知識系統的實施建議

若要把本次研究結果真正落到系統流程，建議先從**流程編排與品質閉環**兩條線同步推進。流程編排層面，應在 `process_video.py` 或後續重構版處理器內加入清楚的分流規則：先嘗試現成字幕提取，若無結果或結果過短，再自動切換至 ASR；若 ASR 結果中的專有名詞密度高、疑似錯字多，則再進一步導向具上下文修正能力的模型。品質閉環層面，則要把逐字稿來源、命中方式、處理耗時、成本估算與人工抽檢結果落庫，讓未來可以根據真實數據調整策略。[1] [3] [4]

| 實施面向 | 建議做法 | 目的 |
| :--- | :--- | :--- |
| 流程分流 | 先 Apify，失敗再 ASR | 降低平均成本 |
| 來源標記 | 保存 transcript_source、fallback_level | 便於後續分析效果 |
| 品質指標 | 記錄字數、標點率、疑似英文品牌命中率 | 快速判斷可用性 |
| 熱詞管理 | 為騰訊雲建立品牌/工具熱詞表 | 提升專有名詞命中率 |
| 抽檢機制 | 每批抽樣人工複核若干影片 | 驗證真實品質 |
| 可擴展性 | 預留 FunASR 接口層 | 避免未來重構成本過高 |

## 9. 最終結論

本次整合調查已經把兩件事講得很清楚。第一，斗影知識系統當前摘要品質不穩，根源在**逐字稿上游品質不足**；第二，TikHub `fetch_one_video_v2` 在本次樣本中**無法作為抖音原生字幕來源**。因此，系統不應再押注單一字幕提取方案，而應正式切換為**分層逐字稿策略**。[1] [2]

在這個策略下，**Apify** 負責低成本優先抓取現成字幕，**騰訊雲 ASR** 負責中文主力轉寫，**GPT-4o-mini** 負責高語義複雜度內容補底，而 **FunASR** 則作為未來可評估的自建演進方向。這樣的結構同時兼顧了成本、中文品質、專有名詞辨識與系統可擴展性，也最符合斗影知識目前從「可用摘要系統」邁向「可信知識系統」的實際需求。[3] [4]
