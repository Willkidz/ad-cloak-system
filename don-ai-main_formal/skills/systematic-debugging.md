> **TL;DR**: 本技能是 SOP 3 Debug 流程的增強版，提供五步系統性除錯指南：現象分析（客觀記錄，禁止猜測）→ 多假設生成（至少 3 個不同方向）→ 驗證計劃（優先快速證偽）→ 執行與反思（連續失敗 3 次觸發反思機制，含歷史錯誤模式比對）→ 修復與記錄（實際測試 + 記錄至 `.ai/error-log.md`）。核心反模式包括執著偏差、確認偏差和沉沒成本。

# 系統性除錯流程（增強版）

> 本技能封裝了 [`00-系統索引/common-cmd.md`](../00-系統索引/common-cmd.md) 中的 SOP 3（Debug 流程）與 [`.ai/prompts/debug-prompt.md`](../.ai/prompts/debug-prompt.md) 的完整內容，並在此基礎上新增了增強功能。原始文件保持不變，本技能為增強補充版。

## 觸發條件

- 遇到 Bug 或錯誤需要排查時
- 功能測試未通過需要定位原因時
- 用戶報告了異常行為需要診斷時
- 部署後發現服務異常時

## 前置知識

- 必須先讀取 [`.ai/error-log.md`](../.ai/error-log.md)，確認此錯誤是否與過去遇到的問題相似
- 必須先讀取 [`.ai/memory.md`](../.ai/memory.md) 中的系統狀態快照，了解當前環境
- 根據錯誤所在的模組，載入對應的專案文檔（先讀 `_index.md`）

## 具體步驟

### 步驟 1：現象分析（Observation）

<step id="debug-step-1">

客觀描述你看到的錯誤現象、日誌內容和相關代碼片段。

**必須做的**：
- 記錄完整的錯誤訊息和錯誤碼
- 記錄錯誤發生的時間和環境（測試版/正式版）
- 記錄觸發錯誤的具體操作步驟
- 記錄相關的代碼片段（含文件路徑和行號）

**絕對禁止的**：
- 在此階段提出任何關於根本原因的猜測
- 跳過此步驟直接開始修復

</step>

<example>

```
## 現象分析
- **錯誤訊息**：[完整錯誤訊息]
- **錯誤碼**：[HTTP 狀態碼 / 錯誤代碼]
- **發生環境**：[測試版 / 正式版 / 本地開發]
- **重現步驟**：
  1. ...
  2. ...
- **相關代碼**：[文件路徑:行號]
```

</example>

### 步驟 2：多假設生成（Hypothesis Generation）

<step id="debug-step-2">

基於現象，列出至少 3 個**完全不同方向**的潛在根本原因。

**假設方向參考（從不同維度思考）**：

| 維度 | 可能的方向 |
| :--- | :--- |
| 代碼邏輯 | 語法錯誤、邏輯錯誤、類型錯誤、邊界條件 |
| 環境與依賴 | 版本不匹配、配置錯誤、環境變數缺失 |
| 外部服務 | API 變更、網路異常、第三方服務故障 |
| 資料問題 | 資料格式不符、資料庫表結構變更、資料遷移遺漏 |
| 部署問題 | 部署版本錯誤、快取未清除、Worker 綁定錯誤 |

</step>

<example>

```
## 多假設列表
- **假設 A（代碼邏輯）**：[描述] — 合理性：[為什麼可能]
- **假設 B（環境/依賴）**：[描述] — 合理性：[為什麼可能]
- **假設 C（外部服務）**：[描述] — 合理性：[為什麼可能]
```

</example>

### 步驟 3：驗證計劃（Verification Plan）

<step id="debug-step-3">

針對每個假設，提出具體的驗證步驟。**優先執行能快速證偽的步驟**。

**原則**：
- 每個假設至少有一個可執行的驗證步驟
- 優先選擇能在 1 分鐘內完成的驗證
- 驗證步驟必須是可觀察的（有明確的通過/失敗標準）

</step>

<example>

```
## 驗證計劃
- **驗證假設 A**：[具體命令或操作] → 預期結果：[如果假設正確會看到什麼]
- **驗證假設 B**：[具體命令或操作] → 預期結果：[如果假設正確會看到什麼]
- **驗證假設 C**：[具體命令或操作] → 預期結果：[如果假設正確會看到什麼]
```

</example>

### 步驟 4：執行與反思（Execution & Reflection）

<step id="debug-step-4">

根據驗證計劃逐步執行。

**關鍵規則**：
1. 每次獲得新資訊後，必須明確聲明：「這個新證據**支持了假設 X**，並**排除了假設 Y**」
2. 如果當前假設被證偽，**立即停止在該方向上的嘗試**，轉向列表中的下一個假設
3. **反思機制觸發條件**：如果連續 3 次嘗試都失敗，必須：
   - 暫停所有操作
   - 輸出自我反思：「我之前的假設可能都錯了，因為…」
   - 重新回到步驟 1，重新審視現象
   - 生成全新的假設（不能與之前的假設重複）

**增強：錯誤模式比對**

在執行驗證前，先檢查 [`.ai/error-log.md`](../.ai/error-log.md) 中是否有類似的錯誤模式：
- 相同的錯誤碼？
- 相同的模組或文件？
- 相同的操作場景？

如果找到匹配，優先嘗試歷史解決方案。

</step>

### 步驟 5：修復與記錄（Conclusion & Fix）

<step id="debug-step-5">

只有在某個假設得到充分證據支持後，才提出具體的代碼修復方案。

**必須做的**：
1. 解釋為什麼這個修復能解決根本問題
2. 說明如何避免未來再次發生
3. 執行修復後，必須實際測試驗證（遵循 SOP 2 的測試規範）
4. 將完整的除錯過程記錄到 [`.ai/error-log.md`](../.ai/error-log.md)

</step>

<example>

```
## [YYYY-MM-DD] 錯誤標題
- **現象**：[簡述]
- **根本原因**：[最終確認的原因]
- **排除的假設**：[列出被證偽的假設及原因]
- **修復方案**：[具體做了什麼]
- **預防措施**：[如何避免再次發生]
- **相關文件**：[涉及的文件路徑]
```

</example>

## 驗證方式

- [ ] 已列出至少 3 個不同方向的假設
- [ ] 每個假設都有對應的驗證步驟
- [ ] 已明確記錄每個假設的證實/證偽過程
- [ ] 若連續失敗 3 次，已觸發反思機制
- [ ] 修復後已實際測試並提供證據
- [ ] 已將完整除錯過程記錄到 `.ai/error-log.md`

## 常見陷阱

<rule id="debug-anti-patterns">

| 陷阱 | 說明 | 解法 |
| :--- | :--- | :--- |
| 執著偏差 | 鎖定第一個想到的原因，忽略其他可能性 | 強制列出 3 個假設 |
| 確認偏差 | 只找支持自己假設的證據 | 優先嘗試證偽 |
| 沉沒成本 | 在一個方向上花了很多時間就不願意放棄 | 失敗 3 次強制反思 |
| 忽略歷史 | 不看 error-log.md 就開始除錯 | 步驟 4 增強的錯誤模式比對 |
| 只改不測 | 修完代碼就報完成 | 步驟 5 強制實際測試 |

</rule>
