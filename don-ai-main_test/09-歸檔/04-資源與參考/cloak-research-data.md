## 第一部分：市場與開源方案研究

本部分對比了現有的開源斗篷項目和商業服務，分析其優劣，為自建方案的技術選型提供依據。

### 1. 開源方案與商業服務分析 (ID:19)

> **核心發現**：GitHub 上缺乏現成的 Cloudflare Worker 斗篷方案，但 `YellowCloaker` (PHP) 提供了極佳的參考，其包含管理後台、3.7萬筆 Bot IP 庫、GeoIP 功能與 A/B 測試。商業方案月費從 $19 到 $330+ 不等，但業界共識是自建反向代理長期最穩定，因公開方案易被集體偵測。

<rule id="cloaking-platform-selection">
**最佳平台選擇**：Cloudflare Worker 原生支援 GeoIP (國家/城市/ASN)，無需依賴 MaxMind 或第三方 API，是部署斗篷引擎的最佳平台。
</rule>

**可複用資源**：
- **IP 庫**：`YellowCloaker` 的 `bots.txt` (37,385 條 CIDR)。
- **IP 列表**：`SecOps-Institute/FacebookIPLists` (每日更新)。
- **User-Agent 規則**：`pycloaker` 的 Bot UA 正則表達式 (超過 80 種)。

### 2. 未來功能需求 (ID:35)

參考火鳥廣告系統的不足，規劃未來斗篷系統應具備的功能：

- **廣告製作優化**：在廣告設定頁面增加「複製」按鈕，允許一鍵複製整筆廣告配置（如名稱、主題、連結、QR code 等）。
- **域名管理優化**：在域名解析頁面增加「批量新增」功能，支援一次性提交多個域名。

### 3. 主流廠商功能對比 (ID:302)

對火鳥斗篷及超過 15 家全球斗篷廠商（如 Keitaro, Binom, Adspect, Cloakerly 等）進行了橫向對比。

- **分析維度**：涵蓋了火鳥的 9 大核心功能、18 項設定、`gotolink()` 機制與定價。
- **功能矩陣**：建立了詳細的功能對比表，包含基礎過濾、高級防護、流量路由及內容整合等維度。
- **研究報告**：詳細報告存放於 `firebird-cloaker-research.md` 和 `cloaker-research-report.md`。

## 第二部分：系統架構與設計

本部分詳細闡述了基於 Cloudflare 的 Serverless 斗篷系統架構設計、開發階段規劃與核心原則。

### 1. 建議架構 (ID:19, ID:182)

採用完全的 Serverless 架構，以達到高可用性、低維護成本和彈性擴展。

| 組件 | 技術選型 | 職責 |
| :--- | :--- | :--- |
| **核心引擎** | Cloudflare Worker | 執行所有過濾邏輯，處理請求分流。 |
| **規則/日誌** | Cloudflare D1 | 儲存過濾規則、黑白名單及詳細的訪問日誌。 |
| **動態配置** | Cloudflare KV | 存放 Bot IP 黑名單等需要快速讀取的配置。 |
| **管理後台** | Cloudflare Pages | 提供用戶界面，用於管理活動、查看日誌和調整規則。 |
| **自動化任務** | n8n / Cron Worker | 定期更新 IP 信譽庫、備份數據等。 |

**核心過濾邏輯**：

<step>IP 白名單檢查</step>
<step>IP/ASN/User-Agent 黑名單檢查</step>
<step>地理位置 (國家/地區) 過濾</step>
<step>使用 `proxycheck.io` API 偵測 VPN/Proxy</step>
<step>使用 `BotD.js` 進行客戶端指紋識別</step>

<rule id="cloaking-no-redirect">
**無重新導向原則**：Worker 不應使用 302 重新導向，而是直接 `fetch` Money Page (落地頁) 的內容並以串流方式回傳，實現無縫的反向代理模式。
</rule>

### 2. 六階段開發任務 (ID:304, ID:317)

專案將分六個階段進行，逐步實現完整功能。

- **Phase 0**: **基礎設施**。建立 D1 資料表 `cloak_logs` 和 KV `CLOAKER_CONFIG`。
- **Phase 1**: **ASN 過濾**。攔截 Meta (AS32934, AS63293) 和 Google (AS15169) 的爬蟲，導向安全頁，並非同步寫入日誌。
- **Phase 2**: **UA/Referrer 過濾**。從 KV 讀取過濾規則，避免硬編碼。
- **Phase 3**: **參數傳遞優化**。確保 `fbclid` 等所有查詢參數能完整附加到目標 URL。
- **Phase 4**: **JS 指紋挑戰**。引入基於 WebGL、AudioContext 和 WebGPU 的多信號指紋評分，通過者 IP 加入短期白名單。
- **Phase 5**: **反向代理實現**。在同一域名下綁定落地頁和安全頁，支援靜態模式 (KV/R2) 和代理模式 (`fetch` 外部 URL)。

### 3. 開發與審核SOP (ID:305, ID:307, ID:316, ID:319)

為確保開發品質與系統穩定性，制定了以下核心規則。

<rule id="cloaking-rule-1">
**歸因隔離原則**：斗篷的過濾邏輯絕對不能影響現有的廣告歸因流程。即使訪客被攔截，帶有有效參數的請求仍需保留基礎日誌記錄。
</rule>

<rule id="cloaking-rule-2">
**動態配置原則**：所有黑白名單 (IP/ASN/UA) 必須儲存在 D1 或 KV 中，嚴禁在 Worker 腳本內硬編碼。
</rule>

<rule id="cloaking-rule-3">
**非同步日誌原則**：所有流量日誌的寫入操作必須使用 `ctx.waitUntil()` 以非同步方式執行，絕不阻塞主請求的處理流程。
</rule>

<rule id="cloaking-rule-4">
**無縫透傳優先**：Phase 5 完成後，應優先使用 Reverse Proxy 模式，避免因 301/302 重定向導致的效能損耗和追蹤參數遺失風險。
</rule>

<rule id="cloaking-rule-5">
**安全頁合規原則**：安全頁內容必須看起來完全合規，且與廣告素材的主題具備明確的關聯性。嚴禁使用空白頁、錯誤頁或不相關的內容。
</rule>

## 第三部分：安全策略與反偵測

本部分聚焦於 Meta 的反斗篷機制，並提出相應的安全策略與最佳實踐。

### 1. Meta 反斗篷偵測機制 (ID:311, ID:315)

Meta 在 2025-2026 年採用了更先進的偵測手段：

- **無頭瀏覽器執行**：能夠完整執行 JavaScript，使得傳統的客戶端斗篷失效。
- **AI 視覺比對**：透過 AI 分析廣告素材與安全頁的視覺內容，判斷其語義是否一致。
- **住宅代理審核**：使用大量住宅 IP 進行審核，使得單純的數據中心 IP 黑名單失效。
- **週期性重新爬取**：在廣告的整個生命週期內會進行多次重新爬取，不能在通過初次審核後關閉防護。

### 2. 安全策略與最佳實踐 (ID:183)

<rule id="cloaking-best-practice-1">
**域名策略**：只使用 `.com`, `.net`, `.org` 等通用頂級域名，名稱看起來像品牌，不含敏感詞。每個 Campaign 使用獨立域名，並定期輪換（建議 2-4 週）。
</rule>

<rule id="cloaking-best-practice-2">
**安全頁 (Safe Page) 策略**：內容必須逼真，與廣告內容相關，並包含隱私政策頁面。禁止在同一流量來源重複使用域名、素材或安全頁。
</rule>

<rule id="cloaking-best-practice-3">
**帳號隔離**：使用多個獨立的 Cloudflare 帳號分散風險，新帳號需使用新的 Email 和付款方式，不與舊資產產生關聯。
</rule>

<rule id="cloaking-best-practice-4">
**主動監控**：投放前必須使用 Meta 分享偵錯工具 (`developers.facebook.com/tools/debug/`) 預檢域名健康狀況。
</rule>

### 3. 風險等級與應對手冊 (ID:185)

| 風險層級 | 觸發條件 | 應對措施 |
| :--- | :--- | :--- |
| **Meta 層 (最高)** | 廣告被拒 / 帳戶被禁 | 立即棄用域名，更換新域名和 Safe Page 模板，隔離所有關聯資產。 |
| **Cloudflare 層** | 收到濫用投訴 | 將域名解析至空白頁，回覆投訴，並棄用該域名。 |
| **公共聲譽層** | 進入 VirusTotal/Spamhaus 黑名單 | 直接棄用域名，申訴成本過高。 |
| **註冊商層 (最低)** | 收到 DMCA 投訴 | 根據情況更換內容或棄用域名。 |

### 4. 備份與反關聯性防護 (ID:184)

- **備份策略**：Worker 代碼使用 Git 提交至私有倉庫；D1 數據透過 Cron Worker 定期匯出 SQL Dump 至 R2；Pages 前端與 DNS 設定同樣納入版本控制。目標是實現 15 分鐘內快速重建。
- **反關聯性**：新購域名必須開啟 WHOIS 隱私保護。每個 Campaign 使用不同的 Safe Page 模板和素材風格，避免模式化。

## 結論

本次研究全面地勾勒出自建廣告斗篷系統的技術路徑與實施策略。研究表明，**基於 Cloudflare Worker 的 Serverless 架構是當前兼具成本效益、效能與反偵測能力的最優解**。相較於市面上的商業方案，自建系統雖然需要前期投入，但能提供完全的規則掌控權、更佳的整合性與長期穩定性，並能有效規避因共享方案導致的連帶風險。

接下來的關鍵是按照規劃的六個階段穩步推進開發，特別是**嚴格遵守歸因隔離、動態配置與非同步日誌等核心開發原則**。同時，持續關注 Meta 的反偵測技術演進，並將域名輪換、資產隔離等安全策略制度化，是確保斗篷系統長期有效的根本保障。
