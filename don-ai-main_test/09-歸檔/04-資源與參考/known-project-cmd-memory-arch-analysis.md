# 「廣為人知」專案指令與記憶系統架構分析報告

## 摘要

本報告針對「廣為人知」專案的現有指令 (`project_guangwei_instructions.md`) 與 D1 記憶資料庫中的實際記錄進行深度分析。報告首先肯定了現有架構在數據驅動、記憶整合及成本控制方面的優點，隨後指出了五大核心缺漏：缺乏系統化的審核測試框架、素材測試科學性不足、記憶分類系統存在斷層、未定義端到端的工作流程 (SOP)，以及競品分析與測試假設之間缺乏轉化機制。最後，報告提出了一系列具體的優化建議，旨在補全架構短板，提升 Meta 廣告素材測試與審核的系統化程度與效率。

## 一、 現有架構的優點

<rule>
現有架構中值得保留和發揚的優點包括：

### 核心理念明確且嚴格
現有指令強烈強調 **「數據驅動」** 與 **「客觀表達」**，嚴禁主觀判斷（例如「我覺得」），這對於建立科學化的測試系統至關重要。

### 記憶系統整合度高
採用 D1 資料庫作為記憶中樞，並強制要求任務開始前讀取、獲得結論後寫入，確保了知識的累積與跨任務共用。

### 具備基礎的測試與分析框架
已定義了素材版本命名規則（如 `CS01-v1`）、變動類型分類（文字、視覺、意思、受眾、格式），以及封號素材的拆解比對流程。

### 強烈的成本控制意識
在指令中多次強調降低 Token 消耗，並針對圖像生成流程制定了具體的省 Token 規範（例如「直接生成，不需要說明設計思路」）。
</rule>

## 二、 核心缺漏與深度分析

透過比對專案核心目的與現有指令、記憶記錄，發現以下按重要性排序的關鍵缺漏：

### 1. 缺乏系統化的「Meta 審核測試框架」與「狀態定義」

*   **缺漏描述**：現有指令僅提到「封號素材分析流程」，但未明確定義審核狀態的層級。在實務上，Meta 審核有「正常上架」、「審核卡住（長時間未過）」、「拒絕刊登 (Rejected)」、「帳號停權 (Banned)」等多種不同狀態。
*   **記憶印證**：記憶記錄 (ID:133) 提到「博富三種框架素材全部禁止刊登」，但指令中缺乏針對「禁止刊登」與「封號」的差異化處理邏輯。`[待確認]`
*   **影響**：無法精準定位是素材元素違規，還是觸發了更嚴重的帳號層級懲罰。同時，缺乏一個「已知安全/危險元素」的規則庫結構。

### 2. 素材測試的科學性落實不足

*   **缺漏描述**：雖然指令規定「每次素材變動只能測試一個變數」，但缺乏 **「控制組 (Control Group)」** 的概念。沒有明確指示必須保留一個「已知可過審/成效穩定」的版本作為基準對照。
*   **記憶印證**：記憶記錄 (ID:135) 提到「測素材框架時不能一次上三張，必須一次一張」，顯示實務上曾發生變數控制不佳的情況。`[待確認]`
*   **影響**：若無控制組，當測試版本成效下降或被拒絕時，難以確認是單一變數的影響，還是整體環境（如大盤波動、帳號權重）的變化所致。

### 3. 記憶系統的分類不足與追蹤斷層

*   **缺漏描述**：現有 `category` 包含 `test_result`, `ban_analysis`, `competitor_analysis`, `creative_pattern`, `credentials`, `issue_resolved`。但缺乏專門用於儲存「Meta 審核規則知識庫」與「素材版本歷史/族譜」的分類。
*   **記憶印證**：記憶記錄中出現了 `convention` 類別 (ID:134, 136, 137)，這在指令的 `category` 可選值中並未定義，顯示現有分類已不敷使用。`[待確認]`
*   **影響**：審核規則散落在 `ban_analysis` 或 `convention` 中，難以系統化檢索；素材版本的演進缺乏結構化的關聯記錄。

### 4. 整體工作流程 (SOP) 定義不夠連貫

*   **缺漏描述**：指令中包含了各個片段的規則（測試、封號分析、競品），但缺乏一個從「發想 → 製作 → 上架 → 監控 → 分析 → 迭代」的完整端到端標準作業流程 (SOP)。
*   **記憶印證**：記憶記錄 (ID:134) 特別新增了「素材製作流程：先確認方向再生圖」，這本應屬於整體 SOP 的一環，卻以零散的記憶形式存在。`[待確認]`
*   **影響**：AI 在執行任務時可能缺乏全局觀，容易在不同階段間產生斷層或重複操作。

### 5. 競品分析轉化為測試假設的機制未明

*   **缺漏描述**：指令中的「BigSpy 競品素材流程」僅提到「仿製改寫」與「記錄追蹤」，但未定義如何將競品的特徵（如特定的 CTA、視覺引導）系統化地轉化為我們自己的「測試假設」。
*   **影響**：競品分析容易流於表面的模仿，而未能提煉出可驗證的底層邏輯。

## 三、 具體優化建議

針對上述缺漏，建議對 `project_guangwei_instructions.md` 進行以下結構性優化：

### 建議一：建立「Meta 審核狀態分級」與「規則知識庫」

<step>
1.  **定義審核狀態**：在指令中明確區分「正常過審」、「審核延遲 (>24h)」、「拒絕刊登 (Ad Rejected)」、「帳號停權 (Account Banned)」。
</step>
<step>
2.  **新增記憶分類**：在 D1 記憶系統中正式新增 `meta_policy_rule`（Meta 審核規則庫）分類，專門記錄哪些字眼、圖片元素是「紅線（高風險）」、「黃線（中等風險）」或「綠線（安全）」。
</step>
<step>
3.  **優化分析流程**：當發生拒絕刊登時，除了拆解元素，必須強制查詢 `meta_policy_rule` 進行比對，並更新該知識庫。
</step>

### 建議二：強化 A/B 測試的科學框架

<step>
1.  **強制設立控制組**：在【素材測試系統】中新增規定：每次測試必須包含一個「控制組 (Control)」（已知表現穩定或可過審的版本）與一個「實驗組 (Variant)」。
</step>
<step>
2.  **細化測試記錄**：要求在記錄測試結果時，必須同時列出控制組與實驗組的數據對比（例如：實驗組 CTR 2.5% vs 控制組 CTR 1.8%），而非僅記錄單一數據。
</step>

### 建議三：擴充並標準化記憶系統 Category

<step>
1.  **更新指令中的 Category 列表**：將實務上已在使用的 `convention`（專案慣例/流程規範）正式納入指令。
</step>
<step>
2.  **新增 `asset_lineage` 分類**：用於記錄素材的演進關係（例如：`CS01-v2` 繼承自 `CS01-v1`，修改了標題），建立素材族譜。這有助於未來追溯某個成功特徵的起源。
</step>

### 建議四：制定端到端的「廣告生命週期 SOP」

在指令中新增一個【標準工作流 (SOP)】章節，將現有零散的規則串聯起來：

<example>
*   **Phase 1: 假設與發想** (查記憶 → 提假設 → 決定變數)
*   **Phase 2: 製作與確認** (文字描述方向 → 用戶確認 → 生圖/文案)
*   **Phase 3: 上架與設定** (設定控制組與實驗組 → 確保單一變數)
*   **Phase 4: 監控與記錄** (度過學習期 → 記錄數據 → 寫入 `test_result`)
*   **Phase 5: 審核異常處理** (觸發拒絕/封號 → 啟動拆解分析 → 更新 `meta_policy_rule`)
</example>

### 建議五：深化競品分析的轉化邏輯

修改【BigSpy 競品素材流程】，增加「特徵萃取與假設生成」步驟：

<example>
規定在分析高成效競品後，必須輸出：`【競品特徵假設】：我假設競品使用 [某特徵] 是因為 [某心理機制]，我們將在 [素材ID] 中測試此特徵。`
</example>

## 結論

> **總結來說，現有架構已具備良好的數據驅動基礎。透過補足「審核狀態分級」、「控制組機制」與「端到端 SOP」，將能大幅提升測試的嚴謹度與過審率，使「廣為人知」專案真正成為一個可自我進化的廣告優化系統。**
