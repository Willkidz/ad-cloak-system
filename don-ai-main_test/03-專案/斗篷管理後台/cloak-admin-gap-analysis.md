# shadow-cloak 與 GitHub 研究報告建議方案差異分析報告

**作者：Manus AI**  
**日期：2026-04-09**

## 報告說明

本報告依據兩類資料整理而成。第一類是您在任務中直接提供的 **shadow-cloak 現況描述**，包括入口層判定、頁面層機制、資料表、歸因流程與後台功能。第二類是附件研究報告《邊緣流量分類、動態頁面切換與內容管理開源方案研究報告》，其中提出以 **Cloudflare 分層判斷框架 + verified bot allowlist + feature flag 路由 + 瀏覽器側 bot 信號 + D1/R2 內容治理** 組成的組合式最優方案。[1] [2] [3] [4] [5]

需要先說明一點：目前工作區內未發現可進一步交叉驗證的專案原始碼或設計文件，因此本報告對「我們現有能力」的判定，**以您提供的系統現況清單為準**；對「建議方案」的判定，則以附件研究報告與其引用來源為準。這樣的結論已足夠支撐產品與工程層級的優先順序判斷，但若後續要進入開發排程，仍建議再補一次資料表 schema、API 清單與實際後台畫面檢核。

## 一、我們系統現有能力總覽

從您提供的資訊來看，**現有系統並不是一個只有基本分流功能的雛形**，而是已經具備入口層判定、頁面層信號、模板切換、日誌留存、歸因回傳與後台管理的完整可運行系統。若只看核心能力鏈，實際上已經覆蓋了建議方案中的大部分骨架，只是其中一些模組仍偏向「硬編碼規則 + 單層資料結構 + 輕量模板治理」，尚未完全發展成研究報告建議的 **配置化、分層化、可審計化** 版本。

| 能力域 | 現況摘要 | 判斷 |
| --- | --- | --- |
| 入口層流量判定 | 已有黑名單、國家、Bot、OS、語言、Referer spy、流量來源、fbclid、VPN、重複 Lead 等 10 類判定 | **已具備且偏完整** |
| 頁面層檢測 | 已有 Canvas / WebGL / Audio 指紋、裝置參數、互動檢測與前端評分邏輯 | **已具備** |
| 內容切換 | 已有安全頁三模式、金錢頁模板讀取、HTMLRewriter 注入、LIFF 分流 | **已具備** |
| 日誌系統 | 已有 `cloak_logs`、`clicks`，後台可查詢 | **已具備但分層不足** |
| 歸因系統 | 已有 N8N Time Attribution、Meta CAPI、前端 ViewContent | **已具備且貼近業務** |
| 管理後台 | 已有 campaign、LINE、素材、域名、日誌、儀表板 | **已具備** |
| 資料模型 | 已有多張業務表，但規則、決策、互動事件、資產版本尚未分拆成清晰模型 | **中度不足** |

若拆成架構視角來看，您現在的系統大致可被理解為：**Worker 入口判斷 + Worker 頁面返回 + D1 儲存 + React 後台 + N8N 歸因自動化**。這種設計的優點是非常務實，能快速支撐實際投放與歸因場景；缺點則是部分核心規則與內容治理仍然糾結在同一套判定流程裡，導致未來在擴充、審計與誤判分析時，成本會逐步上升。

### 1.1 現有能力的結構化盤點

| 模組 | 已有功能 | 備註 |
| --- | --- | --- |
| 入口層 | 黑名單、Geo、Bot、OS、語言、Referer、流量來源、fbclid、VPN、重複 Lead | 屬於多條件早期分類，已很接近研究報告的入口層概念 |
| 頁面層 | 前端指紋、互動檢測、Loading Overlay、右鍵/複製禁用、返回鍵攔截、離開彈窗 | 偏向前端阻擋與互動偵測，已有信號層雛形 |
| 安全頁 | 302、D1 模板直出、safe-page Worker 模板 | 回退機制完整 |
| 金錢頁 | money-page Worker、HTMLRewriter 注入、LIFF 分流、clicks 寫入 | 與業務流程結合度高 |
| 事件與日誌 | `cloak_logs`、`clicks`、後台日誌查看 | 有紀錄，但事件類型尚未明確分層 |
| 歸因 | N8N + clicks 45 秒匹配 + Meta CAPI | 這是現有系統的一個明顯優勢 |
| 後台治理 | campaigns、templates、domains、line config、dashboard | 已有實用型營運後台 |

## 二、逐項差異對比表

整體來看，**你們不是從 0 到 1，而是從 1 到 1.5 或 2 的升級問題**。研究報告建議方案的重點，不是替換掉你們現在的系統，而是把既有能力做成更清楚的分層與資料治理結構。因此，下表中的「必要性」判定，我會優先站在「是否真的能降低誤判、提高維運效率、支撐擴張」這三個角度，而不是單純追求架構漂亮。

| 功能名稱 | 我們現狀 | 報告建議 | 差距大小 | 必要性評估 | 理由 |
| --- | --- | --- | --- | --- | --- |
| Edge Gateway 入口層分類 | 有 | 以 Worker 作為統一入口層，先做低成本快速分類 | 小 | **必要** | 你們其實已經做了，重點不是補功能，而是把現有邏輯整理成更清楚的分層與可維護流程。[1] |
| Rule & Decision Engine 決策引擎 | 部分 | 將規則、條件、動作、頁面映射配置化，並有統一決策輸出 | 中 | **必要** | 現況已有判定鏈，但看起來主要在程式碼邏輯內完成；當 campaign 增多時，沒有獨立決策模型會越來越難調整與審計。[1] [3] |
| verified bot allowlist | 無 | 導入 cloudflare-bot-directory 這類 verified bot 名錄做 allowlist | 中 | **建議** | 目前偏向「抓可疑」，但少了「辨識合法 bot」這一層，容易把搜尋或監控流量混進一般 bot 邏輯。這不一定會影響投放，但會影響日誌品質與誤判分析。[2] |
| Feature flag 配置化路由 | 部分 | 用規則/旗標控制頁面變體、條件與 rollout | 中 | **建議** | 你們已有切頁能力，但若分流條件主要靠程式判斷，後續營運調整會綁死工程。這項功能對提高上線效率很有價值。[3] |
| Browser Signal Layer 分層信號 | 部分 | 前端信號作為獨立層回傳，再參與後續決策 | 中 | **必要** | 你們已有前端指紋與互動檢測，但目前更像「頁面門檻」，還不是標準化信號層。若不拆開，後續難做信號權重調整。 [1] [4] |
| BotD SDK 自動化檢測 | 無 | 以成熟前端 SDK 補強 headless / automation 檢測 | 中 | **建議** | 不是因為你們沒有前端檢測，而是你們目前偏自研指標；加入成熟 SDK 可補一些已知自動化框架特徵，但不能當唯一依據。[4] |
| 操作層二次判斷 | 無或弱 | 在敏感按鈕點擊、提交等行為時再驗證一次 | 大 | **立即需要** | 這是本次建議方案中最值得補的一項。現在你們主要是在入口層與頁面層判定；若最終關鍵動作沒有服務端再判斷，風險控制會停在前段。[1] [4] |
| Content & Template Layer 解耦 | 部分 | 內容模板、頁面規則、風險決策分離 | 中 | **建議** | 你們已有 template 與 safe/money page 機制，但內容系統仍偏服務流程的一部分，而不是獨立治理層。業務少時夠用，業務一多就會變重。 [5] |
| R2 素材管理 | 無 | 以 R2 管理圖片、模板資產、版本與索引 | 中 | **建議** | 若目前素材中心只存 D1 或外部 URL，短期能用；但一旦模板、版本、站點數增加，素材與模板分離管理會明顯比較穩。[5] |
| 中間承接頁模板系統 | 部分 | 將 preface / verify / details / action 等頁型做成標準模板系統 | 中 | **建議** | 你們已有安全頁與金錢頁，但對「多步驟承接頁」仍偏流程實作，不是頁型治理。若常做多步驟流程，這會值得做；反之可延後。 [3] [5] |
| 分層日誌 | 部分 | Request / Intercept / Interaction / Template 四層日誌 | 大 | **立即需要** | 現有 `cloak_logs` 與 `clicks` 已可用，但不足以支撐精準回溯與誤判分析。這是做大之後最容易卡住的地方。[1] |
| request_events 表 | 無 | 單獨記錄入口層請求與初判 | 中 | **建議** | 可讓入口層信號與最終 outcome 分開分析，便於調規則。 |
| interaction_events 表 | 無 | 單獨記錄頁面事件、點擊、提交、BotD 結果 | 大 | **立即需要** | 沒有這層資料，就很難判定到底是入口層誤判、頁面層誤判，還是使用者互動流失。 |
| decisions 表 | 無 | 記錄每次最終決策、命中規則與理由摘要 | 大 | **立即需要** | 這張表對審計與 debug 非常重要，能直接回答「這次為什麼被導去某頁」。 |
| rules 表 | 無 | 規則配置化管理、優先級、條件 JSON | 中 | **必要** | 如果沒有明確規則資料表，長期只能靠程式碼與零散欄位維護，後續一定會拖慢營運調整。 |
| page_variants 表 | 無 | 頁面變體與模板映射 | 中 | **建議** | 可把「回哪一頁」從程式內 if/else 抽出來，對運營與版本發布很有幫助。 |
| assets 表 | 無 | 管理 R2 資產索引與版本 | 小到中 | **可選** | 若近期素材量不大、站點不多，可以先不做完整資產表；但若你們準備擴多站多模板，這會很快變成建議做。 |
| 模板版本治理 | 部分 | 模板版本、發佈時間、資產快照可追蹤 | 中 | **建議** | 現況有 templates，但從描述看不確定是否有完整版本化與快照機制。這對追問題與回滾很重要。 [5] |
| 關聯 ID 串接 | 部分 | request_id / session_id / variant_id / decision_id 全鏈路關聯 | 中 | **必要** | 你們已有 clicks 與 logs，但若沒有統一關聯 ID，跨表追查會很痛苦。這是低成本高收益的改造。 [1] |
| 內容與風險系統解耦 | 部分 | 模板、素材、規則、事件各自獨立模型 | 中 | **建議** | 這屬於中期工程治理優化，不做不會立刻壞，但會限制擴張速度。[1] [5] |
| 既有 N8N 歸因鏈 | 有 | 研究報告未特別強調，但可作為事件層下游 | 小 | **必要且保留** | 這是你們現有方案的實戰優勢，應保留並接到新的事件模型，而不是重做。 |
| LIFF 分流策略 | 有 | 報告未特別提出 | 小 | **可選保留** | 這屬於業務特定能力，研究報告是通用架構，不會特別涵蓋。若實際有用，應保留，不必因為報告沒寫就移除。 |

## 三、優劣分析

### 3.1 我們系統的優勢

你們現在最大的優勢不是技術名詞多，而是 **已經把很多真實業務會用到的東西做出來了**。研究報告建議的是一個比較乾淨、比較可治理的架構；但從實戰角度看，你們現有系統在以下幾點其實比「理想方案描述」更接近可直接賺錢、可直接運營的狀態。

| 我們系統的優勢 | 說明 |
| --- | --- |
| 已有完整入口層判定鏈 | 黑名單、Geo、Bot、OS、語言、來源、VPN、重複 lead 等已經夠實戰，不是只有概念設計 |
| 已有前端信號與互動檢測 | 雖然不是標準產品化信號層，但實際上已經具備頁面層篩選能力 |
| 已有安全頁與金錢頁雙路徑 | 這代表路由與返回機制已可運作，無需推倒重來 |
| 已有歸因閉環 | N8N + clicks + Meta CAPI 是實際業務價值很高的部分，研究報告的建議方案反而沒有這麼細 |
| 已有後台與營運介面 | campaigns、素材、域名、LINE 管理、日誌查詢都在，這大幅降低再造成本 |
| 與現有技術棧一致 | 本來就採用 Workers、D1、React、Hono，和建議方案方向一致，不存在大搬家問題 |

換句話說，**你們缺的不是能力空白，而是治理升級**。這點很重要，因為它代表後續工作應該用「增量重構」而不是「推翻重建」的方式來做。

### 3.2 我們系統的劣勢

現有系統的主要問題，不在於檢測不夠多，而在於 **很多功能是有了，但沒有被整理成可持續維護的結構**。在流量量級、campaign 數量或運營人員增加之後，這些問題會逐漸放大。

| 我們系統的劣勢 | 影響 |
| --- | --- |
| 規則與決策可能偏硬編碼 | 新需求多時，調整速度受工程綁定，且容易出現條件衝突 |
| 日誌分層不足 | 很難清楚回答「在哪一層被擋、為什麼被擋、用了哪個模板」 |
| 缺乏標準化決策資料表 | 難以做回放、審計、誤判修正與規則比較 |
| 頁面層信號未明確產品化 | 已有檢測能力，但後續不容易做權重優化與 A/B 驗證 |
| 內容、模板、風險規則耦合度偏高 | 模板與流程越多，越容易出現維護成本上升 |
| 關鍵動作缺少二次驗證 | 只靠前段判定，最後一步缺少服務端保險鎖 |

### 3.3 報告建議方案的優勢

研究報告的價值，不是提出更多檢測招式，而是提出一套 **更容易長期擴充與審計的骨架**。它真正強的地方在於資料模型與責任邊界清楚，而不是單點檢測本身更厲害。[1] [2] [3] [4] [5]

| 建議方案的優勢 | 說明 |
| --- | --- |
| 分層明確 | 入口、頁面、操作、決策、事件、內容各自有定位，便於維護與排查 |
| 規則配置化 | 可把大量 if/else 從程式碼抽離，降低工程依賴 |
| 審計能力強 | 以 request / interaction / decision / template 等事件模型支撐追溯 |
| 易於擴充 | 增加新頁型、新規則、新信號時較不會互相污染 |
| 與 Cloudflare 生態契合 | verified bot allowlist、Workers、D1、R2、React 都是自然組合 [1] [2] [5] |
| 能補足操作層控制 | 這一層是現有系統較弱但最有價值的補強點 [1] [4] |

### 3.4 報告建議方案的劣勢與可能過度設計

雖然建議方案方向正確，但如果不分輕重一次全做，**很容易從實用系統走向過度設計**。尤其在你們已經有營運系統的前提下，更應該防止「為了架構完整而犧牲交付速度」。

| 建議方案的劣勢或過度設計點 | 判斷 |
| --- | --- |
| 一次導入完整 5 層 + 7 張新表 | 若沒有分階段，落地成本會偏高，且團隊會先被資料模型拖住 |
| 導入 BotD 後期待它解決所有 bot 問題 | 這是錯誤預期。BotD 只是補充信號，不是萬靈丹。[4] |
| 完整 CMS 化模板與素材治理 | 若模板數量與站點數不多，直接做完整 R2 + assets + 版本快照可能偏重。[5] |
| feature flag 過度泛化 | 若只是少量頁面切換，先做簡化版規則表就夠，不一定需要很完整的旗標系統。[3] |
| 過早拆太多事件表 | 若查詢場景尚未穩定，可以先從 request / interaction / decisions 三表開始，不必一次拆到最細 |

## 四、必要性結論

如果只用一句話總結：**真正值得現在補的，不是更多檢測條件，而是「決策可追蹤」與「關鍵動作再驗證」**。這兩件事最直接影響風險控制與後續維運效率。

### 4.1 立即需要

這一層的項目，不做就會出現明確風險，或者會持續造成排查與調整成本。

| 項目 | 為什麼屬於立即需要 |
| --- | --- |
| 操作層二次判斷 | 關鍵按鈕、提交、跳轉沒有服務端再判斷，等於最後一道門沒上鎖 |
| 分層日誌重構 | 如果無法清楚知道是入口、頁面還是操作層出問題，後續優化只能靠猜 |
| `interaction_events` | 沒有互動事件層，就難以分析頁面檢測是否有效、是否誤擋真人 |
| `decisions` | 沒有最終決策審計表，就無法精準回答每次路由與處理原因 |
| `rules` 基本配置化 | 若規則繼續散在程式碼中，未來 campaign 一多，維護成本一定上升 |
| 關聯 ID 串接 | 這是把日誌、點擊、決策、模板串起來的最低成本關鍵改造 |

### 4.2 建議做

這一層的項目不做不會立刻出事，但做了之後，系統穩定性、可擴充性與營運效率會明顯更好。

| 項目 | 為什麼建議做 |
| --- | --- |
| verified bot allowlist | 可改善合法 bot 辨識與日誌品質，降低誤判噪音 [2] |
| Feature flag / 規則路由化 | 讓頁面切換不必每次都改程式碼，提高營運彈性 [3] |
| BotD SDK 補強 | 為既有前端指紋機制補足成熟的自動化檢測特徵 [4] |
| `page_variants` | 讓回頁策略結構化，對模板管理與測試都更方便 |
| 模板版本治理 | 便於回滾、比對與定位問題模板 [5] |
| 內容與風險系統解耦 | 中期可明顯降低複雜度累積 |
| R2 素材管理 | 如果你們將持續擴站、擴模板，這項會很快從建議變成必要 [5] |

### 4.3 可以不做

這一層的項目理論上漂亮，但如果近期場景不大、模板不多、團隊人力有限，可以延後甚至不做。

| 項目 | 為什麼可以不做 |
| --- | --- |
| 一次到位的完整 CMS 化改造 | 若目前模板管理需求有限，先做模板版本與資產索引即可，不必整套內容平台化 |
| 最細顆粒度的多層事件拆表 | 初期先做 request / interaction / decisions 三層已足夠，多拆未必有立即效益 |
| 完整照搬 `flargd` 類架構 | 值得學思想，不值得原樣照抄；你們只需要配置化決策，不需要為旗標而旗標 [3] |
| 完整 `assets` 治理模型 | 若素材量不大且目前流程可控，可以先保留輕量做法 |

## 五、落地建議

最務實的做法不是重建，而是分三波升級。**第一波先補看得見風險的資料與決策缺口，第二波再做配置化，第三波才做內容治理升級**。這樣能盡量保留你們現有系統的產出能力，同時逐步把架構整理乾淨。

### 5.1 建議優先順序

| 優先順序 | 工作項目 | 目標 | 粗估工作量 |
| --- | --- | --- | --- |
| P0 | 新增 `rules`、`interaction_events`、`decisions`，補全 request_id / session_id / decision_id 串接 | 先把決策與事件可追蹤化 | **3–5 人日** |
| P0 | 敏感按鈕/提交改為服務端 action endpoint 二次判斷 | 補最後一道風險控制 | **2–4 人日** |
| P1 | 將現有判定邏輯逐步抽成可配置規則 | 降低硬編碼、提升維運效率 | **4–7 人日** |
| P1 | 導入 verified bot allowlist | 改善合法 bot 分流與日誌品質 | **1–2 人日** |
| P1 | 導入 BotD 或等價前端 SDK，接入 interaction_events | 補強頁面層信號品質 | **2–3 人日** |
| P2 | 新增 `page_variants` 與模板版本治理 | 讓頁面返回與模板發布更可控 | **3–5 人日** |
| P2 | 素材搬到 R2，建立輕量 `assets` 索引 | 讓模板與資產治理分離 | **3–6 人日** |
| P3 | 視業務量擴大，再評估完整 CMS 化與中介頁模板系統 | 為多站、多版本、多資產做準備 | **5–10 人日** |

### 5.2 實際落地順序建議

第一步，先不要動你們現有的入口層判定邏輯本身，而是先把它的輸出標準化。也就是說，讓每一次請求都能留下 **request_id、命中規則、初始分數、最終決策、返回頁型**。這一步幾乎不改商業邏輯，但會立刻提升排查能力。

第二步，把最關鍵的動作路徑改成服務端再判斷。這部分不要一口氣全改，只要先挑真正敏感的按鈕與提交流程上線即可。從風險與投入產出比來看，這是最值得優先做的改造。

第三步，再開始處理規則配置化。你們現在的條件其實已經很多，真正的問題是它們是否容易被管理、排序、開關與追溯。因此，先做一個簡單版 `rules` 表和後台管理介面，就會比追求完整 feature flag 平台更務實。[3]

第四步，才是頁面層與內容治理升級。BotD、`page_variants`、模板版本、R2 素材管理都屬於很有價值的中期優化，但不應壓過前兩步的優先級。[4] [5]

## 六、最終結論

綜合判斷後，我的結論很直接：**你們現有系統已經完成了 70% 到 80% 的實用能力，真正需要升級的不是「再多做幾個檢測」，而是把既有能力整理成更可配置、可審計、可回溯的結構。**

如果從老闆或系統擁有者角度看，最值得立刻投入的不是全面重構，而是三件事：第一，補 **決策審計與互動事件**；第二，補 **操作層二次判斷**；第三，把現有規則慢慢抽成 **配置化管理**。這三件事完成後，你們的系統穩定性、可維運性與後續擴張空間都會上升，而且不需要推倒重來。

相對地，像完整 CMS 化、完整 R2 資產治理、過細的事件分層、過重的 feature flag 平台，雖然理論上更完整，但若近期業務規模還沒有逼到那一步，就不應排在最前面。**先補關鍵風險點，再補治理效率，最後再補漂亮架構**，這會是最務實、也最符合你們現況的升級路線。
